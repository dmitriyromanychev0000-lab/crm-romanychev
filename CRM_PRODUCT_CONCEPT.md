# CRM PRODUCT CONCEPT — зафиксированная логика продукта

Статус: рабочий источник требований, согласованный в диалоге с владельцем CRM на 2026-09-27.

Этот файл фиксирует **бизнес-логику и UX-смысл CRM**. Он не заменяет `AGENTS.md` и визуальные концепты, а имеет приоритет перед случайными текущими реализациями, если они противоречат описанной здесь логике.

> Важно: всё в разделе «Подтверждено» уже согласовано. Всё в разделе «Открытые вопросы» нельзя додумывать молча — это нужно уточнить в дальнейших вопросах.

---

## 1. Назначение CRM

CRM предназначена для личной мобильной работы мастера по ремонту техники.

Основные задачи:
- быстро создать и закрыть заявку прямо с телефона;
- хранить историю клиентов, работ, гарантий, фотографий и расходов;
- вести локальный склад;
- считать личный заработок по заявке;
- формировать акт выполненных работ только когда он нужен клиенту;
- хранить данные локально и иметь надёжные резервные копии.

CRM проектируется **только под телефон, 320–430 CSS px**.

# ПОДТВЕРЖДЕНО

## 2. Общий UI / визуальная логика

### 2.1. Меню

Не раскрашивать каждый пункт меню своим отдельным цветом.

Нужна спокойная цельная палитра без «радуги» и цветного шума. Цвет применяется осмысленно для состояний, акцентов, ошибок и важных действий, а не как уникальный цвет для каждого пункта.

### 2.2. Качество компоновки

Интерфейс не должен выглядеть как набор случайно набросанных карточек.

Нужны:
- понятная сетка;
- одинаковые выравнивания;
- нормальная визуальная иерархия;
- компактность без тесноты;
- аккуратные иконки;
- предсказуемые действия;
- минимум лишних подписей и кнопок.

Пример замечания: текст внутри элемента «Добавить материал без склада» не должен быть прилеплен к верхнему левому углу — он должен быть визуально нормально выровнен внутри элемента.

## 3. Жизненный цикл заявки

При создании заявки используются ровно три рабочих статуса:
- **В работе**;
- **Закрыта**;
- **Отказ**.

Дополнительные статусы сейчас не нужны.

Закрытую заявку можно потом редактировать как обычную — отдельный режим «Внести исправление» не требуется.

### 3.0. Даты заявки

- дата создания автоматически ставится сегодняшняя, но её можно изменить вручную;
- для статуса **В работе** дата закрытия пустая;
- при переключении в **Закрыта** дата закрытия автоматически ставится сегодняшняя;
- **Отказ** считается закрытой заявкой, поэтому дата закрытия также автоматически ставится сегодняшняя;
- отдельное поле «Причина отказа» не нужно — при необходимости причина пишется в комментарии мастера.

### 3.1. Сумма

Для обычной закрытой заявки:
- итоговая сумма обязательна;
- итоговая сумма должна быть больше 0.

Для заявки **в работе**:
- итоговая сумма может быть 0;
- предоплата может быть 0 или больше 0.

Для **отказа от ремонта**:
- итоговая сумма может быть 0;
- такая нулевая заявка не должна искажать выручку, средний чек и финансовую статистику по типу техники.

### 3.2. Предоплата

Предоплата — отдельное информационное поле.

Она нужна, чтобы видеть:
- сколько клиент уже дал;
- сколько осталось получить.

Расчёт заработка мастера всегда строится от **полной итоговой суммы заявки**, а не от предоплаты.

## 4. Клиент

Поля:
- имя клиента;
- телефон клиента;

не являются обязательными.

Причины:
- имя клиента может быть неизвестно;
- некоторые партнёрские организации не передают мастеру телефон клиента.

### 4.1. Телефон

Если телефон введён:
- он должен проходить валидацию;
- нельзя сохранять некорректное количество цифр/символов;
- по совпавшему нормализованному номеру CRM должна автоматически находить клиента и подтягивать его известные данные и историю заявок.

При этом **заявку можно сохранить вообще без телефона**.

### 4.2. Пустой клиент

Заявки без телефона/идентификатора клиента нельзя автоматически склеивать в одного «пустого клиента».

Если идентифицировать человека нельзя:
- заявка остаётся самостоятельной записью;
- ей присваивается свой внутренний ID;
- один и тот же адрес сам по себе не является доказательством, что это тот же клиент.

### 4.3. Повторный клиент

Если введён телефон, который уже есть в CRM:
- система автоматически находит существующего клиента;
- привязывает новую заявку к его истории;
- подтягивает имя и другие известные данные;
- подставляет **последний использованный адрес**;
- адрес можно сразу изменить вручную, если текущий выезд в другое место.

Отдельная метка «постоянный клиент» не нужна — история и количество заявок видны в карточке клиента.

В карточке клиента нужно внутреннее поле **«Заметка о клиенте»** для информации вроде особенностей подъезда, домофона и других полезных деталей.

Отдельный поиск именно во вкладке клиентов сейчас не является приоритетом, потому что основной поиск по заявкам уже умеет находить данные клиента.

## 5. Финансовая модель заявки

Используем короткие названия:

- **Серый расход**
- **Белый расход**

Слово «фактический» в интерфейсе не использовать.

### 5.1. Процент по заявке

В каждой заявке есть поле:

**Процент по заявке**

Правила:
- значение по умолчанию: **50%**;
- можно менять вручную для конкретной заявки;
- значение не может быть меньше 0% или больше 100%;
- никаких «Компания A / Компания B» и автоматической привязки процента к организации не требуется.

### 5.2. Расходы

**Серый расход**:
- всегда вводится вручную одной общей суммой;
- никакая складская автоматика его не изменяет;
- поле необязательное и может быть 0.

**Белый расход**:
- одно итоговое поле в заявке;
- автоматически учитывает все добавленные расходы без склада;
- мастер может вручную увеличить итоговый белый расход, чтобы учесть бензин, еду и другие дополнительные траты;
- вручную нельзя поставить белый расход меньше суммы уже добавленных расходов без склада;
- поле может быть 0, если расходов нет.

Ограничения:
- **Белый расход ≤ Серый расход**;
- **Серый расход ≤ Итоговая сумма заявки**;
- отрицательные значения недопустимы.

### 5.3. Формула заработка

Личный заработок по закрытой заявке:

```text
Заработок =
(Итоговая сумма − Серый расход) × Процент по заявке
+ (Серый расход − Белый расход)
```

Пример:

```text
Итоговая сумма: 30 000
Серый расход:   10 000
Белый расход:    3 000
Процент:            50%

База для деления: 30 000 − 10 000 = 20 000
Доля мастера:     20 000 × 50% = 10 000
Разница расходов: 10 000 − 3 000 = 7 000

Заработок: 17 000
```

При закрытии заявки мастер должен сразу видеть, сколько он заработал по этой формуле.

### 5.4. Не делать детализацию расходов обязательной

Для финансовой модели заявки достаточно **двух итоговых сумм**:
- Серый расход;
- Белый расход.

Не требуется отдельная таблица из нескольких строк расходов типа «ремонт платы», «ремонт бака» и т. п. только ради финансового расчёта.

## 6. Склад и расходы

Это принципиально разные вещи.

### 6.1. Покупка на склад

Если мастер купил запчасти/расходники небольшим оптом:
- деньги учитываются в финансовых расходах **в момент закупки**;
- товар приходит на склад.

### 6.2. Резерв и списание склада в заявке

Если складскую позицию добавили в заявку со статусом **В работе**:
- указанное количество сразу уходит в **резерв**;
- зарезервированное количество недоступно другим заявкам;
- нельзя зарезервировать больше доступного остатка.

Если количество в заявке изменили:
- резерв пересчитывается сразу;
- уменьшенная часть немедленно возвращается в доступный остаток.

Если позицию удалили из заявки:
- резерв полностью снимается;
- товар снова становится доступным.

Если позиция остаётся в заявке при её закрытии/отказе:
- зарезервированное количество окончательно списывается со склада.

Финансово это не создаёт новый расход заявки:
- деньги уже были учтены как расход в момент закупки;
- стоимость складской позиции второй раз из заработка заявки не вычитается.

Пример:
- ранее куплены складские детали на 4 000;
- клиент заплатил 30 000;
- белый расход конкретной заявки 3 000.

Для заработка заявки старые 4 000 повторно не вычитаются.

В интерфейсе склада нужны быстрые фильтры:
- Все;
- В наличии;
- В резерве;
- Мало осталось.

Отдельная тяжёлая колонка «В резерве» на основном мобильном экране не нужна; количество резерва можно показывать внутри карточки/деталей позиции.

### 6.3. Расход без склада

Есть расходы, которые нет смысла заводить на склад.

Примеры:
- отдать бак стиральной машины другому мастеру;
- отдать плату на пайку/ремонт;
- разовая работа или деталь, которую мастер не хранит на складе.

Это относится к расходу конкретной заявки, а не к складскому движению.

Позиция расхода без склада хранит:
- наименование;
- количество;
- сумму;
- необязательный комментарий для истории.

Для простых количественных позиций допустим обычный расчёт количества × цены, но складские единицы измерения сюда переносить не нужно.

Сумма таких позиций автоматически входит в минимально допустимый **Белый расход** заявки. Мастер может увеличить общий белый расход вручную, но не уменьшить его ниже суммы расходов без склада.

Текущий UI такого добавления нужно переделать: он должен быть компактным, понятным и визуально выровненным, а не выглядеть как случайно поставленная подпись и отдельное поле себестоимости.

### 6.4. Единицы хранения и списания

При заведении позиции на склад выбирается готовая единица хранения:
- шт;
- кг;
- г;
- л;
- мл.

Пользовательские единицы не нужны.

Для совместимых величин можно один раз настроить отдельную единицу списания:
- хранение в кг → списание в г;
- хранение в л → списание в мл.

CRM сама конвертирует количество. Пример: вместо 0,03 кг в заявке мастер пишет 30 г.

Несовместимые единицы переводить нельзя:
- шт нельзя превращать в л;
- кг нельзя превращать в шт;
- и т. п.

Для позиции в штуках разрешены дробные значения списания: 0,2; 0,3; 0,5 и т. д.

### 6.5. Закупки партиями и FIFO

При закупке можно вводить:
- количество;
- общую сумму закупки.

CRM сама рассчитывает себестоимость единицы.

Повторные закупки одной и той же позиции по разной цене хранятся отдельными партиями.

При списании используется **FIFO**:
- сначала расходуется самая старая партия;
- затем следующая по времени закупки.

Это не меняет финансовую модель заявки: закупка уже была расходом в момент покупки, поэтому списание партии в заявку не создаёт новый расход заявки.

### 6.6. Минимальный остаток и список покупок

Для каждой складской позиции задаётся **Минимальный остаток**.

Когда общий доступный остаток достигает этого значения или опускается ниже:
- CRM показывает предупреждение;
- позиция **автоматически добавляется в список покупок**;
- дубль одной и той же позиции в списке покупок не создаётся;
- количество к покупке по умолчанию ставится равным значению «Минимальный остаток»;
- мастер может вручную увеличить количество к покупке.

Минимальный остаток считается **по товару в целом**, а не отдельно по местам хранения.

### 6.7. Места хранения

Одна складская позиция может одновременно находиться в нескольких местах.

Примеры:
- мастерская;
- машина;
- дом;
- рюкзак;
- другие пользовательские места.

Места хранения настраиваемые:
- добавить;
- переименовать;
- архивировать.

Остаток одной позиции ведётся отдельно по каждому месту хранения, но общий остаток товара — сумма всех локаций.

При списании из заявки должно быть понятно, из какого места хранения взят товар.

Нужно действие **«Переместить»** между местами хранения:
- перемещение не считается закупкой;
- перемещение не считается расходом/списанием;
- меняется только распределение остатков.

Новая закупка может сначала попасть в состояние **«Нераспределено»**, после чего мастер вручную распределяет количество по местам хранения.

## 7. Услуги и прайс

### 7.1. Прайс зависит от типа техники

При создании заявки выбирается тип техники, например:
- холодильник;
- стиральная машина;
- посудомоечная машина;
- и другие существующие типы.

У каждого типа техники свой прайс.

### 7.2. Прайс состоит из блоков/категорий

Пример для холодильника:
- Диагностика;
- Холодильное отделение;
- Компрессор;
- другие тематические блоки.

Внутри блока находятся конкретные услуги.

Пример:
- диагностика;
- выезд/диагностика;
- разбор холодильного отделения;
- замена датчиков;
- проверка датчиков;
- проверка заслонки;
- проверка вентилятора;
- и т. д.

Существующие данные из старого бэкапа нужно использовать как основу. Не придумывать прайс заново без необходимости.

### 7.3. Выбор услуг в заявке

Не нужно делить каталог на:
- «товары»;
- «услуги»;
- «услуга + товар».

Для заявки нужен нормальный выбор работ из прайса.

Сценарий:
1. В заявке нажать «Выбрать услуги».
2. Открывается структурированный каталог.
3. Видны категории/блоки.
4. Внутри — услуги.
5. Можно выбрать **любое количество услуг без лимита**.
6. Выбранные услуги попадают в заявку аккуратным списком/таблицей.

Текущий вариант «накиданных» элементов без ясной сетки не подходит.

### 7.4. Цена услуг в заявке

Мастер **не должен вручную редактировать цену каждой услуги**.

Он:
1. выбирает услуги;
2. вводит/согласовывает с клиентом **итоговую сумму**;
3. CRM автоматически пересчитывает цены выбранных услуг под эту итоговую сумму.

Пересчёт должен сохранять относительную ценность услуг по исходному прайсу.

Базовый принцип:

```text
Коэффициент = Итоговая сумма / Сумма базовых цен выбранных услуг

Новая цена каждой услуги = Базовая цена услуги × Коэффициент
```

Пример:
- сумма базовых услуг = 20 000;
- с клиентом согласовано 30 000;
- коэффициент = 1.5;
- каждая услуга увеличивается пропорционально своей исходной цене.

Диагностика за 500 не должна внезапно поглощать большую часть общей суммы.

После пропорционального пересчёта:
- каждую цену округлять до **10 ₽**;
- остаток от округления автоматически добавлять к самой дорогой услуге;
- сумма всех строк должна строго совпадать с итоговой суммой заявки.

### 7.5. Исторические цены

После закрытия заявки:
- выбранные услуги;
- их пересчитанные цены;
- итоговая сумма

фиксируются в самой заявке.

Если потом прайс изменился, старые закрытые заявки и акты не должны пересчитываться по новому прайсу.

## 8. Гарантия

Блок гарантии должен находиться логично в процессе заполнения заявки — после выбора/описания работ, а не быть спрятан в самом низу формы.

### 8.1. Срок гарантии

Предустановленные варианты:
- Без гарантии;
- 3 месяца;
- **6 месяцев — значение по умолчанию**;
- 9 месяцев;
- 12 месяцев.

### 8.2. На что распространяется гарантия

Это не один общий список на всю CRM.

Набор вариантов зависит от **типа техники**.

Пример:
- для холодильника может быть «компрессор»;
- для стиральной машины «компрессор» показывать бессмысленно.

Выбор делается галочками.

UI:
- компактная сетка;
- обычно 2 столбца;
- 4 пункта → 2×2;
- 6 пунктов → 3 ряда × 2 столбца;
- без длинной вертикальной простыни, если это можно компактно разместить.

Можно выбрать несколько пунктов.

### 8.3. Свободное дополнение

Под готовыми вариантами есть поле, куда мастер может своими словами дописать, на что ещё распространяется гарантия.

При формировании акта:
- выбранные галочки;
- и свободный текст

объединяются в клиентское описание гарантии.

### 8.4. Редактирование списков

В настройках CRM мастер должен иметь возможность сам:
- открыть тип техники;
- изменить список пунктов гарантии;
- добавить пункт;
- удалить пункт;
- переименовать пункт.

Это не должно требовать изменения кода.

---

## 9. Комментарий мастера

В заявке должен быть отдельный **Комментарий мастера**.

Назначение:
- собственные заметки;
- что именно делалось;
- какие части техники трогались/не трогались;
- детали, которые помогут через несколько месяцев понять ситуацию при повторном обращении.

Это полностью внутреннее поле.

Комментарий мастера:
- не печатается в акт;
- не показывается клиенту.

## 10. Фотографии

### 10.1. UI блока

Фотографии в заявке **не обязательны**.

Блок фотографий:
- всегда открыт;
- его нельзя сворачивать/разворачивать;
- фотографии показываются компактными превью;
- превью не должны быть огромными;
- отдельная кнопка «Просмотр» не нужна;
- нажатие непосредственно на фотографию открывает её для просмотра.

### 10.2. Сжатие

При добавлении фотографии CRM должна автоматически:
- уменьшить её до разумного разрешения;
- сжать;
- предпочтительно сохранить в **WebP** или сопоставимом компактном формате.

Цель — не занимать десятки мегабайт оригиналами камеры без необходимости.

### 10.3. Хранение

Фото и остальные данные CRM хранятся локально.

Облачная синхронизация сейчас не нужна.

Для фотографий нельзя полагаться на маленькое строковое хранилище/обычный браузерный кэш. Нужно использовать локальное хранилище, пригодное для больших Blob/файлов (например IndexedDB или существующий эквивалент старой CRM после проверки реализации).

## 11. Резервные копии

### 11.1. Принцип

Само приложение и пользовательские данные — разные вещи.

- Код приложения можно отдельно сохранить/развернуть на другом сервере или компьютере.
- Данные CRM живут в локальной базе.
- Резервная копия данных должна содержать всё необходимое для восстановления CRM, включая фотографии.

### 11.2. Автоматическое сохранение

Не нужен таймер «раз в 5 минут».

Автобэкап должен реагировать на **изменение данных**.

Примеры:
- создана заявка;
- изменена заявка;
- сохранён черновик;
- закрыта заявка;
- изменился склад;
- изменились настройки;
- удалены/заархивированы данные;
- добавлено фото;
- и т. п.

После изменения обновляется резервная копия **текущего дня**.

### 11.3. Ротация

Хранить **10 последних дневных резервных копий**.

Правило:
- в течение одного дня изменения обновляют бэкап этого дня;
- на следующий день появляется новый дневной бэкап;
- в имени/метаданных есть дата;
- когда накопилось больше 10 дневных копий, самая старая автоматически удаляется/заменяется;
- всегда остаются последние 10 дней.

Цель: иметь возможность вернуться к состоянию за один из недавних дней, но не создавать сотни файлов за сутки.

### 11.4. Опасные действия

Удаление заявки и другие разрушительные действия должны требовать явного подтверждения.

---

## 12. Акт выполненных работ

Акт нужен не для каждой заявки. Он формируется, когда клиент его просит.

### 12.1. Хранение

Сам файл/картинка акта не нужно постоянно хранить в CRM.

Сценарий:
1. Открыть сохранённую заявку.
2. Нажать кнопку создания/печати акта.
3. CRM формирует акт из данных заявки.
4. Его можно сохранить как изображение/документ и отправить клиенту.
5. После этого отдельную копию акта внутри CRM хранить необязательно.

Источником истины остаётся сама заявка.

### 12.2. Таблица услуг в акте

В таблице:
- №;
- наименование услуги;
- цена.

Все выбранные услуги печатаются **построчно**, без автоматического объединения или группировки. Если для конкретного акта услуг слишком много, мастер сам меняет состав услуг в заявке перед формированием акта.

Показывается **финальная пересчитанная цена**, с которой заявка была закрыта.

Исходную цену из прайса клиенту показывать не нужно.

### 12.3. Гарантия в акте

Не делать отдельный столбец «Гарантия» напротив каждой услуги.

Это приводило к абсурдным строкам вроде гарантии 6 месяцев на выезд/диагностику.

Вместо этого под таблицей работ формируется отдельный блок гарантии:
- срок;
- выбранные объекты гарантии;
- пользовательское дополнение, если оно заполнено.

Если выбрано **«Без гарантии»**:
- в акте про гарантию ничего не писать.

### 12.4. Комментарий мастера

Комментарий мастера в акт не попадает.

## 13. Настройки

В настройках нужен единый понятный раздел для структуры работы.

Мастер должен иметь возможность самостоятельно редактировать:

### Типы техники
- добавить;
- переименовать;
- изменить связанные настройки.

### Прайс каждого типа техники
- категории/блоки;
- услуги внутри блоков;
- цены;
- добавление/удаление/переименование.

### Гарантии каждого типа техники
- список доступных пунктов «на что гарантия»;
- добавление/удаление/переименование.

Существующий прайс из старых данных нужно импортировать/сохранить, а не заменять новым придуманным набором.

### Источники заявок
В настройках мастер сам ведёт список источников заявок:
- добавить;
- переименовать;
- архивировать.

В заявке выбирается **один источник** из выпадающего списка.

Источник участвует в аналитике:
- количество заявок;
- сумма по заявкам.

Настройки прайса, гарантий, типов техники, источников и склада рассчитаны на владельца этой локальной CRM. Отдельная ролевая система сейчас не нужна.

### Архив вместо удаления
Общее правило для сущностей, которые уже участвовали в истории: **не удалять их физически, а архивировать**.

Это относится как минимум к:
- источникам заявок;
- услугам и категориям прайса;
- типам техники;
- пунктам гарантии;
- местам хранения;
- складским товарам.

Архивная сущность:
- сохраняется в старых заявках, аналитике и истории;
- не предлагается в новых операциях по умолчанию;
- при необходимости может быть восстановлена из архива.

Складской товар с нулевым остатком тоже можно архивировать, не теряя историю закупок, перемещений и списаний.

## 14. Визиты, календарь и напоминания

### 14.1. Следующий визит

У заявки может быть **один следующий визит**.

- дата визита обязательна, если следующий визит назначен;
- время визита необязательно;
- если время не указано, заявка всё равно отображается в календаре на выбранную дату;
- если время указано, длительность по умолчанию — **1 час**;
- длительность можно менять как в меньшую, так и в большую сторону.

Цепочка из нескольких будущих визитов для одной заявки пока не нужна.

### 14.2. Ближайшие визиты

В верхней части CRM должна быть компактная плашка с **3 ближайшими визитами**.

- нажатие на конкретный визит открывает соответствующую заявку;
- в заявке сразу доступны телефон, адрес и остальные данные;
- рядом должна быть отдельная кнопка открытия календаря.

### 14.3. Календарь

Нужен отдельный месячный календарь в тёмном стиле.

- дни с прошедшими визитами сохраняются и отмечаются спокойно/светло;
- дни с будущими визитами выделяются оранжевым акцентом;
- нажатие на день открывает расписание выбранного дня;
- дневная шкала ориентировочно **10:00–22:00**;
- визиты отображаются на своей временной позиции, если время задано.

Если два визита пересекаются:
- CRM предупреждает о конфликте;
- сохранить пересечение всё равно можно.

### 14.4. Просроченные визиты

Если дата визита прошла, а заявка всё ещё не закрыта/не перенесена, CRM должна явно показывать **«Визит просрочен»**.

Просроченный визит должен оставаться заметным до переноса даты или закрытия заявки.

### 14.5. Фокус-напоминания

Ночные системные пуши сейчас не нужны.

При открытии/обновлении CRM нужно показывать фокус-уведомление, если есть:
- визиты сегодня;
- визиты завтра;
- просроченные визиты.

Уведомление можно закрыть.

Если актуальные визиты остаются:
- уведомление снова появляется примерно через **2 часа** активной работы;
- после простоя/закрытия CRM примерно на **30 минут** при следующем открытии уведомление показывается снова.

## 15. Техника, адрес и поиск

### 15.1. Техника в заявке

Нужны только:
- **Тип техники** — холодильник, стиральная машина, посудомоечная машина и т. д.;
- **Название техники** — одно свободное поле, куда можно написать бренд и при необходимости модель, например Samsung RB37.

Отдельные поля:
- модель;
- серийный номер

не нужны.

### 15.2. Адрес

Адрес клиента — одно свободное поле.

Разбивать его на улицу / дом / квартиру / подъезд не нужно.

### 15.3. Глобальный поиск

Нужна одна строка поиска по заявкам, которая ищет сразу по доступным текстовым данным, в том числе:
- имя клиента;
- номер телефона;
- адрес;
- тип техники;
- название/бренд/модель техники;
- другие текстовые данные заявки, где это уместно.

Примеры:
- Samsung → все заявки с Samsung;
- холодильник → все заявки по холодильникам;
- телефон → все заявки найденного клиента;
- имя → все совпадающие заявки.

Рядом с поиском нужны быстрые фильтры:
- Все;
- В работе;
- Закрытые;
- Отказы;
- Сегодня;
- Просроченные.

Отдельный фильтр по типу техники не нужен.

### 15.4. История клиента

Отдельная метка «Постоянный клиент» не нужна.

Если телефон известен, история клиента определяется по нормализованному номеру телефона и доступна в карточке клиента.

- отдельные поля модели и серийного номера;
- отдельная причина отказа;
- лимит на количество выбранных услуг.

## 17. Аналитика

Аналитика — отдельный полноценный раздел CRM.

### 17.1. Периоды

Для аналитики доступны:
- день;
- неделя;
- месяц;
- год;
- всё время;
- свой интервал дат **с / по**.

По умолчанию открывается **месяц**.

При смене периода все карточки, графики и разрезы обновляются синхронно.

### 17.2. Основные финансовые показатели

Использовать простые понятные названия, без лишней бухгалтерской терминологии.

Основные показатели:
- **Получено от клиентов** — итоговые суммы закрытых заявок;
- **Потрачено** — реальные расходы за период;
- **Заработал** — личный заработок мастера с учётом процентов и белых расходов по утверждённой формуле заявки.

В «Потрачено» входят реальные деньги:
- белые расходы по заявкам;
- закупки на склад;
- другие реальные ручные расходы, если они есть в системе.

**Серый расход** в общий показатель «Потрачено» не включается, потому что это не фактическая трата денег.

### 17.3. График по времени

Нужен график доходов/расходов по дням.

Правила:
- по умолчанию отображает текущий выбранный месяц;
- при смене периода обновляется под выбранный интервал;
- дни без заявок можно не показывать пустыми столбцами;
- суммы показываются прямо сверху у соответствующих точек/столбцов, а не только по тапу.

### 17.4. Аналитика склада

Отдельно показывать:
- сколько закуплено за период;
- сколько списано;
- текущую стоимость остатков по себестоимости;
- самые расходуемые позиции.

Топ расходуемых позиций сортировать прежде всего **по количеству списания**, а не по сумме себестоимости.

Складская аналитика не изменяет прибыль заявок и существует как отдельный управленческий разрез.

### 17.5. Типы техники

Нужен разрез по типам техники.

Для каждого типа показывать:
- количество заявок;
- денежный результат/сумму.

Можно использовать переключатель между количеством и суммой.

Показывать весь существующий список типов техники, без искусственного «топ-5».

### 17.6. Средний чек

Средний чек считать по **закрытым заявкам**, исключая статус **Отказ**.

### 17.7. Конверсия

Конверсия показывает долю созданных заявок, которые дошли до статуса **Закрыта**.

Статус **Отказ** считается потерянной заявкой и уменьшает конверсию.

### 17.8. Дни недели

Нужен разрез по дням недели, чтобы видеть загруженность.

Для этой метрики учитывать **все созданные заявки**, а не только закрытые.

### 17.9. Сравнение с предыдущим периодом

Для выбранного периода показывать сравнение с предыдущим сопоставимым периодом.

Примеры:
- день с предыдущим днём;
- неделя с предыдущей неделей;
- месяц с предыдущим месяцем;
- выбранный интервал с предыдущим интервалом такой же длины.

### 17.10. Источники заявок

Источник выбирается в заявке из настраиваемого списка.

В аналитике по каждому источнику показывать:
- количество заявок;
- сумму по заявкам.

Архивированные источники продолжают участвовать в исторической аналитике, но не мешают при создании новых заявок.

# ОТКРЫТЫЕ ВОПРОСЫ

Эти пункты ещё не считаются окончательно согласованными.

1. Правило предоплаты при закрытии:
   - должна ли CRM запрещать закрытие, если предоплата больше итоговой суммы;
   - нужен ли отдельный статус «оплачено не полностью».

2. Точный набор гарантийных пунктов для каждого типа техники.
   Он должен быть восстановлен из старых данных/обсуждён отдельно.

3. Точный шаблон акта:
   использовать ранее предоставленный владельцем пример как визуальную/текстовую основу и не менять формулировки без отдельного согласования.

4. Технический механизм автоматического сохранения дневных backup-файлов в браузере:
   нужно проверить старую реализацию и ограничения браузера/File System Access API перед изменениями.

5. Точная трактовка «Получено от клиентов» в аналитике при частичной оплате/предоплате:
   нужно окончательно решить, отражать ли там договорную итоговую сумму заявки или только реально полученные на текущий момент деньги.
